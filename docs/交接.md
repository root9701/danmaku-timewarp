## 1. 项目是什么

B 站赛事直播的弹幕整夜录下来，第二天对齐到官方回放上，本地网页把录播还原成"正在直播"。

核心设计：**采集时不下载视频，只存弹幕 + 音频指纹**。次日用官方回放的音轨反推
"弹幕第 N 条对应视频第几秒"。一晚弹幕约 10 MB + 指纹约 5 MB。

两个进程：

```
采集端 danmaku-collector/  → 连 B 站 WS 收弹幕 + 拉低清流算音频指纹
播放端 danmaku-server/     → 读赛程找官方回放 BV，逐分P 音频对齐，网页播放
```

## 5. 本轮改了什么（这是最需要你重新判断的部分）

### 5.1 自动校准"永远失败"

**[实测]** 根因两条，都已复核过接口返回：

1. 后端 `/api/autocalign` 成功返回 `{ok, pages}` 但**没有顶层 `offset_sec`**，
   前端判断 `j.ok && typeof j.offset_sec === 'number'` 恒为假 → 一律报
   "自动校准失败: 未知错误"。
2. 前端硬编码 `page: 1`，只对齐第一局。

修法：后端补 `offset_sec`/`confidence`/`page`/`all_ok` 顶层字段；前端改读 `pages`
字典并传 `page: 0`（全部分P）。

### 5.2 单段置信度当门票 → 正常比赛被判失败

**[实测]** 这是"哪一天都不行"的真因。

CFO vs T1 第一局，8 个片段**全部指向同一位置**（离散 0.0 秒），但只有 1 段
`conf=8.28`，其余 7 段是 1.08~2.12（BP/解说段音频特征天然不独特）。
旧逻辑先用 `min_conf` 过滤低分票 → 只剩 1 票 → 达不到 `need=3` → 判"不可靠,已拒绝"。

对照组同样 8 段：拿 26 日回放对 27 日直播，8 段散落在 8 个无关位置，最大簇仅 1 票。

所以判据应该是**"多少段指向同一处"**，不是"每段多有把握"。
修法：改为按投票一致性判定，增加"全票一致且最强票达标"一条。

**[实测]** 采纳条件在 `server.py` 的 `_align_one_page` 里，本轮复核过，共 4 条（满足其一即采信）：

```python
need = max(2, (n_seg + 2) // 3)        # 8 段 → 3 票
strong_conf = max(6.0, min_conf * 3)
if n_vote >= need:                      reasons.append("多段一致")      # ≥3 票
if n_strong >= 2:                       reasons.append("%d 张强票")     # ≥2 张 conf≥6
if max_conf >= 7.0 and n_vote >= 2:     reasons.append("强票+同向")      # 1 强票+2 票
if n_vote == n_seg and max_conf >= min_conf: reasons.append("全票一致")  # 8/8 全指一处
```

第 4 条是实践中最常用的一条（CFO 第一局就是靠它通过的：8 段全指一处，但只有 1 段强票）。

判决后用 `solid.sort(key=lambda c: c[0])` **取最早**的那个候选，
再套时间窗过滤（见 5.5）。窗口外的候选会被标记 `suspect` 并抛错拒绝。

**[待核实]** 这几条阈值我在真实数据上跑通过（26 日 10/10、27 日 8/9），
但**没有构造过对抗用例**去测边界（比如票数刚好 2 vs 3 的差异）。
如果你要调这里，先想清楚会不会让"随机散票"重新通过。

### 5.3 播放时间轴从第二局起错位

**[实测]** 播放器把各分P 首尾相接拼虚拟轴，但官方回放把**局间休息剪掉了**，
所以"虚拟位置"与"真实墙钟"是**分段直线**关系，不是一条直线。

实测偏差（旧单标量 offset 算法）：

| 场次 | 第二局 | 第三局 |
|---|---|---|
| AL vs TLAW | −213.9s | −207.8s |
| TSW vs LOS | −224.9s | — |

修法：逐分P 分段映射（`wallNowMs` / `seekToWallMs` / `recomputeRels`），
局间休息里的弹幕**直接丢弃**而非压缩到相邻分P。

### 5.4 分P 上传顺序 ≠ 时间顺序 → 弹幕整段消失

**[实测]** 26 日 HLE vs IG：P3 赛前评论在时间上**最早**（00:45），上传却排最后
（P1 第一局 01:00 / P2 赛后采访 01:51 / P3 赛前评论 00:45）。

旧 `recomputeRels` 把分段按墙钟排序后套二分查找，算出：

```
00:55 → rel=4106s
01:05 → rel=281s      ← 回退 3800 秒
```

`danmaku` 不再按 `rel` 升序，`upperBound` 二分前提被破坏 → 弹幕整段消失。

修法：每段独立映射（段内必然单调），再按 `rel` 排序。

### 5.5 早上重播干扰

**[实测]** 直播间早上会把前几场重播一遍，音频与官方回放完全一致，投票也会一致命中。
CFO 的 P2「赛前评论」被对齐到 **07:44**（早上重播），距赛程窗口 +405 分钟。

修法：用 `lists[].start_ms`（官方赛程开始时间，由 `/api/discover` 落盘）算时间窗：

```
窗口 = [start_ms - 90分钟, start_ms + 该场全部时长 + 30分钟]
```

**[实测]** 关键细节：搜索必须在 `audiofp.align(valid_range=...)` **内部**限制范围。
第一版我实现成"先取全局最大峰、再按窗口过滤"，结果 26 日 HLE 的 P2/P3 被误杀 ——
窗口内其实有峰（94.1 vs 全局 106.9），只是矮一点，根本没进候选。
这个 bug 是我自己造成的，回头修了一轮。

### 5.6 启动脚本与退出脚本（最后两轮）

**[实测]** 三个问题：

1. `启动回放台.bat` 标题写"仅本机"，实际却绑 0.0.0.0 并打二维码。
   根因：监听地址优先级是 `环境变量 > config.json > 默认`，
   而用户 `config.json` 里存了 `host: "0.0.0.0"`，脚本又没设环境变量。
   修法：脚本里显式 `set DANMAKU_HOST=127.0.0.1`；`main()` 打印实际生效值及来源。
2. 没有退出入口。`e5261a6`「改回前台运行」时把 `停止回放台.bat` /
   `停止采集.bat` / `状态.bat` 全删了。已补回两个 `退出*.bat`。
3. 端口被占用时吐 20 行 traceback。现改为捕获 10048 并给可执行指引。

**[实测]** 实测结果：
- `启动回放台.bat` → 绑 127.0.0.1，局域网访问被拒，无二维码
- `启动回放台_局域网.bat` → 绑 0.0.0.0，局域网 IP 返回 200
- `退出回放台.bat` → 找到 PID 并结束，端口释放

**[已知不可靠]** 写 bat 时踩过：不能在 `for /f` 里嵌套管道 + 多层引号，

```bat
for /f "tokens=5" %%P in ('netstat -ano ^| findstr /r /c:"LISTENING" ^| findstr /c:":8789"')
```

会报 `was unexpected at this time`。现在的写法是**先 netstat 落临时文件，再 findstr**。
另外 bat 必须是 **UTF-8 无 BOM + CRLF**（`.gitattributes` 已固定），
上一轮我第一次写成了纯 LF，cmd 直接跑不了。
