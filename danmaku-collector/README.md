# LOL 延时直播弹幕采集器

一句话说明：把电脑挂在指定的 B 站直播间，整夜自动录制弹幕（含 SC 醒目留言）和**直播音频指纹**（供次日自动对齐），早上拿到一组按整点切片的压缩记录 + 统计摘要。总览见上级目录 `README.md`。

## 控制台（推荐入口）

双击 `控制台.bat`，会自动打开浏览器进入本地控制台页面（http://127.0.0.1:8787），在网页上可以：

- 修改配置（房间号、开始/结束时间、轮询间隔、音频指纹开关、切片周期）并保存
- 一键**测试采集**（默认 60 秒，实时看日志和弹幕计数，验证链路是否正常）
- 一键**开始今晚挂机** / **停止**
- 查看最近一次采集结果摘要

注意：采集运行期间不要关闭黑色控制台窗口（最小化没关系）。`start.bat` 保留为无界面的直接启动方式，效果等同于控制台里点"开始今晚挂机"。

## 日常挂机

1. 睡前双击 `start.bat`（默认 00:30 开始等开播、09:00 自动收尾，config.json 可改）。
2. 窗口最小化即可，**不要关闭**。
3. 早上到 `data/比赛日/` 查看产物；或直接启动 danmaku-server 回放。

## 产物说明（data/目录）

**目录结构：一个会话一个子目录。**

```
data/
  2026-10-25/                          ← 数据日(凌晨录的内容归前一晚)
    2026-10-25_2332_7734200/           ← 会话目录: {数据日}_{开录HHMM}_{房间号}
      7734200_s2332.jsonl.gz           ← 该会话的整点切片
      7734200_s0000.jsonl.gz
      ...
      7734200.afp.jsonl                ← 该会话的音频指纹
      7734200.meta.json                ← 该会话的统计摘要
    2026-10-24_0819_7734200/           ← 同一目录下的另一个会话(白天场), 互不干扰
```

为什么要套这一层：旧布局把同房间的所有会话平铺进 `data/{日期}/`，导致①晚间场与白天场混在一起分不清；②跨零点切片 `_s2332` 与 `_s0000` 按字典序颠倒；③被强杀留下的孤儿 `afp` 无从判定属于哪个会话。会话目录化后，**一个目录 == 一个会话**，切片/指纹/摘要不会串场。

服务端读取层**同时兼容新旧两种布局**（旧平铺数据不用迁移也能读），历史数据可用 `migrate_sessions.py` 一次性整理（默认预演，加 `--apply` 才移动）。

- **会话归属**：凌晨 00:00~11:00 的录制属"前一晚比赛"，目录落在**昨天日期**下（26 日凌晨的会话在 `data/2026-10-25/`）。11 点后的录制落当天目录。**弹幕切片与音频指纹永远在同一会话目录**（同一晚的指纹跟着切片走，自动校准才找得到）。
- `{room}_s{HHMM}.jsonl.gz`：整点切片的弹幕记录（每行一条 JSON：`ts` 毫秒墙钟 / `un` / `t` / `ty`=dm|sc）。`ts` 优先取 B 站消息体里的服务器时间（与本机墙钟差 >6 小时才回落本机时间），避免断线补发导致时间轴失真。
- `{room}.afp.jsonl.gz`：音频指纹（0.2 秒/帧 × 33 频带，整晚约 7MB，不落任何音频）。格式契约见上级 README。
- `{room}.meta.json`：统计摘要（`dm_count`/`sc_count`/`reconnect_count`/`gaps`/`parts` 切片清单/`kw_events` 关键词事件/`ended_by` 结束原因/`write_err_count` 写盘失败丢条数）。
- 同会话重复运行：旧产物自动归档为 `_runN` 后缀，绝不覆盖。**开录时就会检查**会话目录里残留的旧 `meta`/`afp`（上次被强杀、没走到收尾时会留下），先归档再写；`meta` 用临时文件原子替换，不会出现半截 JSON。
- 弹幕写盘失败（磁盘满/句柄失效）会打 `ERROR` 日志并计入 `meta.write_err_count`，连续失败 50 次会明确告警"数据正在丢失"。
- 单实例锁 `logs/collector.lock`：重复启动（含 `--test` 与正式任务并发）会被拒绝并退出码 2，避免两个进程同时写同一数据片。

## config.json 字段说明

| 字段 | 本机当前值 | 说明 |
| --- | --- | --- |
| rooms | [7734200] | 要录制的直播间房间号（整数，可写多个） |
| earliest_start | "00:30" | 最早开始录制时间："HH:MM"/"now"/"+5m" |
| latest_end | "09:00" | 到该时间自动停止录制并收尾 |
| poll_interval_sec | 30 | 未开播时每隔多少秒检查一次开播状态 |
| audio_fp | true | 是否同步录制直播音频指纹（自动校准的数据源；关闭则次日晚只能手动校准） |
| slice_minutes | 60 | 弹幕切片周期（60=整点；0=不切片） |
| data_dir / log_dir | data / logs | 输出目录 |

## 音频指纹 sidecar（live_audiofp.py）

录弹幕的同时拉最低清晰度直播流，只解音频增量计算指纹：

- CPU 增量 <3%，内存约 80MB，磁盘每晚 <10MB，**不落任何音频**。
- 断流自动退避重连（新段重锚墙钟）；任何失败只降级告警，绝不影响弹幕采集主链路。
- ffmpeg 优先用系统 PATH 里的（Termux 兼容），否则用 imageio-ffmpeg 自带二进制。

## 手机备份节点（可选）

`phone_ctl.py`：`status|start|stop|log|pull|test`。与 PC 同时采同一房间互为备份。
依赖：手机装 Termux（python/numpy/brotli/ffmpeg）+ adb 调试；保活需 `termux-wake-lock`、Doze 白名单、**vivo 电池后台高耗电豁免**（未豁免会被 vivo 冻结——实测教训）。数据回传走 `adb reverse` 隧道。

## 测试

```
danmaku-collector\.venv\Scripts\python.exe danmaku-collector\collector.py --test 60
```
`data/当天日期/` 出现 `test_` 开头文件（含 .meta.json，`ended_by`=test_done），不混入正式数据。

## 注意事项

- Windows 电源"睡眠"设为**从不**（半夜休眠会中断采集；代码内置 SetThreadExecutionState 双保险，仅 Windows 生效）。
- 按 Ctrl+C 随时安全停止，已录数据正常收尾。`ended_by`：latest_end（到点）/ interrupt（手动）/ error。
- 若整夜未开播，当天无正式记录属正常（这种情况下**不写** `meta.json`，不会产生 `data/meta.meta.json` 垃圾文件）。
- 复核下播需连续 2 次（间隔 60 秒）`live_status=0`，中间一次恢复即清零——接口抖动不会提前结束录制。
- 滚动切片在收包循环和 1 秒辅助循环里都会检查，断线重连等待期跨整点也能正常切片刻盘。
